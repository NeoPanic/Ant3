## 真实任务暴露的问题与修复

输入为用户原始的十六段古文赋写作要求。两个真实 Run 都只认领、汇报进度并独自写全文，没有发布子任务；两次流式正文均被 HTTP 客户端的 60 秒整次请求上限截断，记录为 `provider_network_error`。历史累计三次此类错误后，Baseline 的候选池目标归零，待重试任务无法再被认领。

- 工作指引要求对可独立产出的多部分成果先建立共同简报，发布有范围和验收条件的子任务；分段写作共享主题、文气、大纲与衔接。首轮拆分后退出，普通蚂蚁在子任务完成后读取完整结果并合稿，沿用现有任务板流程。
- 流式 HTTP 请求保留 60 秒无数据超时，整次请求和 Run 上限改为 600 秒；普通非流式请求仍限 60 秒。超时单独报告 `provider_timeout`。
- 默认输出上限与模型上下文预算的 8192 token 输出预留一致；内部总结继续使用自身显式上限。
- 供应商断连、超时、限流及服务不可用保留失败、重试及能源记录，不计作 Preset 能力失败，也不减弱成果路径信号。既有错误计数通过一次性迁移修正。
- PASS：任务板 21 项、群聊 4 项、分工经验 6 项、自选 3 项回归；另手动执行跨过 60 秒旧上限的真实 HTTP 流测试，62 秒后完整完成。
- PASS：最终改动后再次通过原生 `cargo check --workspace --all-targets --locked` 和 `cargo test --workspace --locked`，依赖边界检查与群聊前端 5 项回归通过。
